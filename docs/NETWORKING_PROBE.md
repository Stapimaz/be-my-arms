# Networking Connection-Lifecycle Probe — Classification

**Purpose:** classify the force-kill "cross-disconnect" observed in M2/M3 (killing one client
disconnects the other, and afterwards the server stops accepting connections).
**Result:** **package-level (NGO/UTP), not a Be My Arms harness bug.** Reproduced with zero game
code.

**Versions:** Unity `6000.4.3f1` · Netcode for GameObjects `2.13.2` · Unity Transport `2.6.0`.

---

## 1. Minimal reproduction (preserved)

Source mirrored under `docs/NetProbe/`; live at `Assets/Scripts/NetProbe/`; scene generated by
`Be My Arms > NetProbe > Build Probe Player` (`Builds/NetProbe/NetProbe.exe`).

It contains **none** of: shared body, bots, role registry, token reclaim, scene synchronization,
auto-reconnect, application conditioner, or Network Simulator. Connection approval is not used. It
is a bare `NetworkManager` + `UnityTransport` with `EnableSceneManagement = false`,
`ForceSamePrefabs = false`, `DisconnectTimeoutMS = 5000`, and connect/disconnect logging.

Usage: `-probe-role server|client`, `-probe-port`, `-probe-exit-after`.

## 2. Evidence

```
baseline:            server listening=True connected=2   (stable for 15 s)
kill client A:
 t=23.0  server   DISCONNECTED id=2  reason=...ProtocolTimeout...
 t=23.46 client B DISCONNECTED id=1  reason=...ClosedByRemote...   <- server closed B
 t=25.3  server   status listening=True connected=1
 t=27.5  server   DISCONNECTED id=1  reason=...ProtocolTimeout...
 t=30.3  server   status listening=True connected=0
launch client C:
 t=35.3  server   status listening=True connected=0               <- C never accepted
```

Baseline with no kill: two clients stayed connected (server `connected=2`); clients do not drop on
their own. Killing one client causes the server to close the other (the healthy client sees
`ClosedByRemote`) shortly after the killed client's protocol timeout, and once both connections are
gone the server no longer accepts a new connection.

## 3. Classification and decision

- The behaviour reproduces in a clean NGO/UTP project with no gameplay, approval, tokens, bots,
  scene sync, conditioner or simulator. **It is therefore a package-level connection-lifecycle
  issue, not a Be My Arms implementation bug.**
- Per project direction, do **not** keep burning development time on it during M3. The minimal
  reproduction is preserved above for a future focused investigation or a Unity bug report.
- **Kept:** the architecture that is correct regardless — role ownership bound at connection
  approval from a token, temporary **bot substitution** for a disconnected role, atomic
  bot→human handoff, and never two owners. A ~5 s disconnect timeout and a client auto-reconnect
  safety net mitigate the symptom.

## 4. Known hardening item (non-blocking)

Force-kill reconnect depends on UTP disconnect detection and connection acceptance, which this
package version appears not to provide cleanly for a peer that is killed rather than closed. This is
tracked as a networking-hardening item to be revisited (e.g. a session/transport layer or a package
upgrade) and does not block M3 gameplay work.
